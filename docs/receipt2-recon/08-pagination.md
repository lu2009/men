## 1. 量测半（要 DOM，不跑，但要说清楚量什么、怎么换算成 px）

原码 `Receipt2.deobfuscated.js:621–665`，一个 `new Promise` 包住，`requestAnimationFrame` 里量完 resolve。

### 1.1 造什么（`:630–645`）

```html
<div style="position:absolute;visibility:hidden;top:0;left:0;">   <!-- 挂在 document.body 上 -->
  <style>«ue(fontSettings, X(printSettings))»
         #r2mp { height: auto !important; overflow: visible !important; }
         #r2mf .receipt2-declaration { flex: 0 0 auto !important; min-height: 0 !important; }
  </style>
  <div class="receipt2-root">
    <section class="receipt2-page" id="r2mp">
      «页头 de(order)»
      <table class="receipt2-table">«表头 re()»<tbody id="r2mb">«每个明细行 ie(line)»</tbody></table>
      <div id="r2mf">«页脚 Ve(order)»</div>
    </section>
  </div>
</div>
```

要点：

- **只造一页**（一个 `.receipt2-page`），里面塞**全部**明细行 —— 目的就是让页面自然长高，一次量完所有行。
- 两条 `!important` 覆盖的作用：正常 `.receipt2-page` 是 `height: Hmm; overflow: hidden`，会把超出的行**裁掉（量不到）**；`height:auto` 让它自然长高，`overflow:visible` 保证不裁。`#r2mf .receipt2-declaration` 那条是防止 `.receipt2-declaration { flex: 1 }` 在测量节点里干扰页脚高度。
- 样式用的是**已提交**的字体 `g`（= `we` 的第二个入参 = `Z(v.value)`）和**已提交**的纸张 `X(h.value)`，不是弹窗草稿。
- 这个 div 挂在 `body` 上，`:663` 量完立刻 `removeChild`。

### 1.2 量什么（`:646–665`）

| 原码变量 | 表达式 | 含义 |
|---|---|---|
| `i` | `#r2mp.getBoundingClientRect().height` | **自然内容高**（页头 + 表头 + 全部明细行 + 页脚 + 页面 padding） |
| `c` | `#r2mp.getBoundingClientRect().width × (heightMm / widthMm)` | **目标页高(px)** —— 见 §1.3 |
| `s` | `#r2mf.getBoundingClientRect().height` | 页脚高 |
| `d` | `Array.from(#r2mb.querySelectorAll("tr")).map(el => el.getBoundingClientRect().height)` | **各明细行高**数组 |
| `V` | `i − Σd − s` | **固定开销**（页面上除明细行和页脚以外的一切）—— 见 §1.4 |
| `u` | `c − V` | `availNoFooter`：不带页脚时留给明细行的预算 |
| `r` | `c − V − s` | `availWithFooter`：带页脚时留给明细行的预算 |

### 1.3 `c = 宽度 × (heightMm / widthMm)` 这个换算为什么成立

**因为 `#r2mp` 的高度被 `height:auto` 覆盖了，量不到「真实一页有多高」，只能从宽度反推。**

- `ue()` 给 `.receipt2-page` 写的是 `width: {widthMm}mm; height: {heightMm}mm`，且 `* { box-sizing: border-box }`，所以 `#r2mp` 的 `getBoundingClientRect().width` **就是 `widthMm` 这个物理长度在 CSS px 下的值**（记作 `Wmm_px`）。
- 于是 `c = Wmm_px × (heightMm / widthMm) = Hmm_px`，即**同一 px 标度下**，一张真实固定高度页面的高度。
- 为什么不直接量？因为测量节点必须让高度 auto 才能量到全部行 —— 两者不可兼得，所以用宽度换。
- 这个写法**对浏览器的 mm→px 标度（DPI / 缩放）免疫**：宽度和高度的换算用同一个标度，比值消掉了。所以 `d`（行高，也是同一标度）和 `c` 可以直接相减比较。
- 有个前提：`#r2mp` 必须保持自己的 `width: Wmm`。真正保护它的是 `ue()` 里 `.receipt2-page { width: {widthMm}mm }` 这条**显式宽度** —— flex 的 `align-items: stretch` 只对 cross-size 为 `auto` 的项生效，显式宽度不会被拉伸（`.receipt2-root` 的 `align-items:center` 只是恰好也保证这点）。**所以移植时只要别把 `.receipt2-page` 的显式 width 去掉、或改成 `100%`/`auto`，这个换算就成立。**

### 1.4 `V = i − Σd − s` 里到底剩下什么

`Σd` 只累加 **`#r2mb`（即 `<tbody>`）里的 `<tr>`** —— 选择器起点是 tbody（`:649` `l.querySelector("#r2mb")`），所以 **`thead` 那行不在这里面**。

因此 `V` 装的是：

```
V = .receipt2-page 的 padding (4mm 上 + 3mm 下)
  + .receipt2-header 高 + 它的 margin-bottom (2mm)
  + .receipt2-meta-row 高 + 它的 margin-bottom (1.5mm)
  + <thead> 那一行高（表头 10 列）
  + .receipt2-table 的 margin-bottom (1.5mm)
  + 边框（border-collapse 下的 1px 线）等零碎
```

一句话：**「页面上除了明细行和页脚以外的一切」**。这就是为什么 `u = c − V` 才是「留给明细行的预算」。**移植时必须把 `thead` 算进固定开销而不是行高**，否则每页会多塞一行。

### 1.5 量测的已知盲点（照抄即可，但要知道）

- **不等图片**。`requestAnimationFrame` 后直接量。二维码 `<img class="receipt2-qrcode">` 是 CSS 定尺 `18mm × 18mm`，所以不影响布局 —— 这一点是安全的前提，**如果以后二维码改成自适应尺寸就必须补等图**。
- **不等 `document.fonts.ready`**。字体栈是系统字体（`Microsoft YaHei, PingFang SC, sans-serif`），风险低；但若有 web font 未就绪，行高会按 fallback 度量，分页结果可能与实打不一致。
- **行高是「自然高度」**，未考虑 `[data-shrink-fit]` 缩字后的回流。明细行没有 shrink-fit（只有客户/电话/安装地址三个 `<span>` 有），无影响。

## 2. 打包半（纯数学，已真跑）

### 2.1 逐字移植对照

原码 `Receipt2.deobfuscated.js:693–714` 用单字母变量；`paginate.mjs` 保留原名并注明映射（`a`/`n` → `rows`/`rowHeights`，`u`/`r` → `availNoFooter`/`availWithFooter`，`i` → `penalty`）。

移植时的一个**简化前提（已核实）**：原码传进来的 `a` 是**订单的明细行数据数组**，但打包循环里**只读了 `a.length`**（切片 `a.slice(t, n)` 在循环外的调用方 `:716–720` 做）。所以 `paginate` 只需要行数，用 `rowHeights` 兼作 `a` 是等价的。

```js
let c = Math.max(0, availNoFooter - penalty);   // 原 :693
let s = Math.max(0, availWithFooter - penalty); // 原 :694
const V = [0];
let y = 0;
for (; y < a.length; ) {
  let e = 0;
  for (let u = y; u < a.length; u++) e += n[u];   // 剩余全部行高之和
  if (e <= s) break;                              // ① 连页脚一起塞得下 → 收工
  let t = 0, l = y;
  for (; l < a.length && !(l > y && t + n[l] > c); ) { t += n[l]; l++; }  // ② 贪心装到 c
  if (
    (l <= y && (l = y + 1),                        // ③「至少前进一行」——死代码，见 §5.1
     l >= a.length && a.length - y > 1 && (l = a.length - 1),  // ④「给最后一页留一行」
     (y = l),
     !(y < a.length))
  ) break;
  V.push(y);
}
```

### 2.2 逐行语义

| 步 | 代码 | 语义 |
|---|---|---|
| 预算 | `c = max(0, u − i)` / `s = max(0, r − i)` | **中间页按 `c`（不带页脚）装；只有最后一页按 `s`（带页脚）判定。** `c ≥ s` 恒成立（因为页脚高 ≥ 0） |
| ① | `if (e <= s) break` | 剩下**所有**行的行高之和 ≤ 带页脚预算 → 全部收进当前页，当前页就是末页（末页是唯一渲染页脚的页，`:719` 的 `n === a.length`） |
| ② | 双条件的 while | 第一个条件 `l < a.length`；第二个 `!(l > y && t + n[l] > c)`。**第一次一定进循环**（`l === y` 使 `l > y` 为假，`&&` 短路，`!false` 为真），所以每页**至少 1 行**。后续是标准贪心：`t + n[l] <= c` 就收 |
| ③ | `l <= y && (l = y + 1)` | 见 §5.1 —— **永不触发** |
| ④ | `l >= a.length && a.length − y > 1 && (l = a.length − 1)` | 见 §5.2 —— 这是「**强制把最后一行留给带页脚的末页**」，与 02 文档写的「别把最后一行单独留下」**语义相反** |
| — | `(y = l)` + `!(y < a.length)` → `break` | 更新游标；若已到末尾就退出（**退出在 `V.push` 之前**，所以不会产生空页） |
| — | `V.push(y)` | 记下新页的起始行 |

**复杂度**：每次翻页都重算一次剩余行高之和（① 的 `for`），所以最坏 `O(n²)`。收据行数是个位数到几十，无实际影响。

## 4. 逐例手工验算

> 每个用例都按「人读规则」独立推一遍，再与程序输出比对。下面写的是**人工推演过程**，不是程序的复述。

设 `len = rows.length`。

**1 · `[30,30,30]` u=100 r=90 → c=100 s=90**
`y=0`：剩余和 `e=90`。`90 <= 90` → ① break。`pages=[0]`。
人推：三行总共 90，正好等于带页脚预算 → 一页。**一致**。

**1b · `[30,30,35]` u=100 r=90 → c=100 s=90**
`y=0`：`e=95 > 90` → 不 break。② 贪心：收 30（t=30,l=1）→ 30+30=60 ≤ 100 收（t=60,l=2）→ 60+35=95 ≤ 100 收（t=95,l=3）→ l=3=len 停。`l=3`。
③ `3<=0` 假。④ `3>=3` 真 且 `3-0=3 > 1` 真 → `l = 3-1 = 2`。`y=2`，`2<3` → push 2。`pages=[0,2]`。
`y=2`：`e=35 <= 90` → ① break。
人推：总高 95 > 90，页脚装不下，**这一页不可能是末页**；可末页必须存在（页脚只在末页渲染），所以至少要留 1 行给它 → 第一页只能拿 `[30,30]`，末页 `[35]`+页脚。**一致**。

**2 · `[50,50,30]` c=100 s=90**
`y=0`：`e=130 > 90`。② 收 50（l=1）→ 检查 `50+50=100 > 100`？假 → 收（t=100,l=2）→ `100+30=130 > 100` 真 → 停。`l=2`。④ `2>=3` 假。`y=2`，push 2。
`y=2`：`e=30 <= 90` → break。`pages=[0,2]`。
人推：判据是 `>` 不是 `>=`，所以「刚好等于 `c`」算**装得下** → 前两行 100 留在第一页。**一致**。

**2b · `[50,50.01,30]` c=100 s=90**（与 2 只差 0.01）
`y=0`：`e=130.01 > 90`。② 收 50（l=1）→ `50+50.01 = 100.00999999999999 > 100` → **真** → 停。`l=1`。④ `1>=3` 假。`y=1`，push 1。
`y=1`：`e=50.01+30=80.01 <= 90` → break。`pages=[0,1]`。
人推：超 0.01 就被拒绝，切分点从 2 掉到 1，**页数不变但分法完全不同**。**一致**。
> 浮点核对：`50 + 50.01` 在 IEEE754 下是 `100.00999999999999091`，仍 `> 100`，与十进制意图一致。我另外在 `0.1` 网格上搜了「十进制和 > 100 但浮点和 ≤ 100」的对，**一组都没找到** —— 所以在 `getBoundingClientRect` 给出的 0.01–0.1px 粒度上，这个严格 `>` 的行为符合十进制意图。（**INTERPRETED**，只在搜过的范围内成立。）

**3 · `Array(10).fill(30)` c=100 s=90**
`y=0`：`e=300>90`。② 收 30/60/90，`90+30=120>100` 停 → `l=3`。④ `3>=10` 假。push 3。
`y=3`：`e=210>90` → `l=6`，push 6。`y=6`：`e=120>90` → `l=9`，push 9。
`y=9`：`e=30<=90` → ① break。`pages=[0,3,6,9]`。
人推：每页 3 行（90 ≤ 100），末页剩 1 行 30 ≤ 90。4 页。**一致**。

**3b · 13 行 × 30** → 同样的节奏走到 `y=12`（`e=30<=90` break），`pages=[0,3,6,9,12]` → 5 页。**一致**。

## 5. 反直觉 / 看着像 bug 的地方（这类比用例本身有价值）

### 5.1 补丁③ `if (l <= y) l = y + 1` 是**死代码**

**结论**：**永不触发。CONFIRMED（代码 + 200,000 组随机模糊实测）**

**证明**：② 的 while 条件第一项 `l > y`，而 `l` 初值就是 `y`，所以第一次判定时 `l > y` 为 **假** → `&&` 短路 → 整个 `!(…)` 为 **真** → 循环体必然执行一次 → `l` 变成 `y+1`。因此循环退出时**恒有 `l ≥ y+1`**，`l <= y` 永远不成立。
除非 `a.length <= y`（`l < a.length` 先失败）——但外层循环已经保证 `y < a.length`。
实测：45 次翻页决策 + 644,400 次翻页决策（模糊）中触发 **0** 次。

**这意味着**：「每页至少一行」这个保证**不是**由③提供的，而是由②「第一次一定进循环」提供的。移植时可以安全地删掉③，但**注释必须写对**（02 文档写的是「保证至少前进一行」，虽然结果正确，但归因错了）。

### 5.2 补丁④ 的注释/描述**与语义相反**——它恰恰是把最后一行单独留下

**结论**：**`if (l >= len && len - y > 1) l = len - 1` 的真实语义是「强制把最后一行切出去，留给带页脚的末页」。CONFIRMED**

02 文档 `02-render-pipeline.md:268` 写的是：

```
if (l >= len && len - y > 1) l = len - 1   // 别把最后一行单独留下
```

**这句话是反的。** 看用例 1b：`[30,30,35]`，三行本来都能塞进第一页（95 ≤ c=100），补丁硬把 `l` 从 3 改到 2，于是 `[35]` 被踢到第二页**独自一行**。所以它是「**制造**最后一行单独一页」，不是「避免」。

**它的真实作用**（这才是不能删的原因）：页脚（金额 + 说明）**只在最后一页渲染**（`:719` 的 `isLast = end === len`）。而 ① 已经确认「剩余总和 > s（带页脚预算）」，所以**当前这一页不可能是末页** —— 必须给真正的末页留至少一行，否则页脚无处安放。没有这个补丁，`[30,30,35]` 会变成一页（95 行高 + 页脚），页脚被挤出页面。

**命名建议**（新版实现时）：`// 必须给带页脚的末页留至少一行`。

### 5.3 补丁④ 只退**一行**，够不够？—— 够，但不能解决「单行超页」

**CONFIRMED**：④ 从不退第二行。这看起来危险，其实是**最优的**：
设末页 = `[最后一行]`，其行高 `h`。若 `h + 页脚高 > 页高`，那么退两行、三行也救不了（`h` 是正的，多退只会让末页更满）。所以「退到只剩最后一行」已经是能做到的**最大化利用当前页**的方案，且是**唯一**能保证末页至少有内容的选择。

**但它救不了**「**单行本身就超过一整页**」：用例 4 / 4b / 4c / 8b / 8c / 8f 都出现了 `⚠溢出` 的页。行为是**溢出（内容被裁）+ 不死循环 + 不报错**。
👉 **新版需要决定**：这种行要不要切分 / 缩字号 / 至少给个告警。旧版是静默裁掉的。**这是我在本次分析里发现的最值得产品决策的点。**

### 5.4 「中间页塞满、末页很空」是常态，不是 bug

中间的页按 `c`（**不带**页脚）装，末页按 `s`（**带**页脚）——而 `s < c`。加上 ① 「剩余全部 ≤ s 才收工」，末页往往只有 1–2 行。
实测：用例 3（10 行）→ `3/3/3/1`；用例 3b（13 行）→ `3/3/3/3/1`；用例 8e（50 行）→ 16×3 + 2。
这是**设计使然**（页脚占位），但如果新版觉得「末页太丑」想改成「尽量填满、页脚另起一页」，那是**有意偏离旧版**，要记进偏差文档。

### 5.5 「0 高行独占一页」是规则允许的

用例 8f：`[0,5,0]` 在 `c=s=0` 下分成 `[0]` / `[5]` / `[0]`，第 0 页是一个 **0 高**的行。
成因还是②的「第一次一定进循环」——它只保证**前进**，不保证**装得下**。极端预算下会出现「空页」（视觉上）。
真实场景里 `c`/`s` 是几百 px、行高几十 px，不会走到这一步；这一条是**边界行为的完整性证明**，不是要修的东西。

### 5.6 严格 `>` 的边界是「刚好等于 = 装得下」

`t + n[l] > c` 用严格大于，所以 `t + n[l] === c` 时**收**（用例 2），`=== c + 0.01` 时**拒**（用例 2b）。移植时若写成 `>=`，每页都会少装一行。**这是最容易写错的一处。**

## 7. 未确认

1. **`c` 的换算在非 96dpi 环境下的实际表现未实测。**
   推理上 `c = Wmm_px × (Hmm/Wmm)` 与 px-per-mm 标度无关，所以 DPI/缩放免疫（**INTERPRETED**）。但我没有在真实浏览器里跑过测量节点，未验证 `getBoundingClientRect().width` 在 `width: {W}mm` 下是否恒等于 `W × (96/25.4)` CSS px（不同浏览器对 mm 的舍入可能有 ±0.5px 差异）。这个误差会被 `c` 放大 `heightMm/widthMm` 倍（对 200×140 横版是 0.7 倍，对 A4 纵向是 1.41 倍）。**建议新版实现时在目标浏览器上校一次。**

2. **`V` 的正负号未实测。** 理论上 `V > 0`（页头 + padding + 表头 + margin），代码也没有 `max(0, …)` 保护。如果 `V` 为负（例如页脚被量成负高、或 `Σd` 因某种原因大于 `i − s`），`u`/`r` 会变大、每页多装行。我无法在静态分析里排除，**但也没找到能造成它的真实路径**。

3. **真实数据下的行高分布未知。** 本报告的 `c`/`s` 是我编的（100/90）。真实值取决于 `widthMm`、`heightMm`、浏览器 px-per-mm、以及明细行的实际换行数。**要判断「旧版一张收据实际分几页」，必须用 r2-config 那边的黄金样本量一次真机 DOM。** 我这里只验证了**算法本身**对所有数值输入的行为。

4. **`radius` / `radius+` 的更细浮点边界未穷举。** 我只在 0.1 网格上搜过「十进制和 > 100 但浮点和 ≤ 100」的翻转（0 命中），没做更细的网格或针对其它 `c` 值的搜索。**INTERPRETED，只在搜过的范围内成立。**

5. **`penalty` 从 `i`（`:667–692`）到 `c`/`s` 的传递链已按代码逐字核对，但 `i` 的**业务意图**仍未确认**（为什么只有 90mm 高的纸减 1px；`a5-*` 是漏写还是有意）。见 `03-print-chain.md` §5.4 与 §11.3。
