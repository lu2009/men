# 打印列取件：按部件 `key` 还是 `materialName`？（2026-09-15）

> 缘起：用户要求「模板中每列部件显示和排序再做一轮验证」。
> 排序已验证通过（见 `docs/2026-09-15-parts-order-fidelity.md` §5.1），
> 但在核对「显示」时发现**取件谓词的字段用错**。

---

## 1. 结论（已确证的一处）

旧版所有打印列遍历公式部件都用 `Object.entries(parts)`，**第一个元素 `e` 是部件 KEY**，
**显示名才取 `t.materialName`**。我们多处用 `p.materialName` 同时承担了「匹配」和「显示」两件事。

以「亮窗/扣板」列为例（引擎 B 生产单 @`Hui-d088417c.js:492734`）：

```js
Object.entries(_0x1d6087)
  .filter((([e]) => ["扣板", _0x11f592(995), _0x11f592(1080), "压线"].some((t) => e.includes(t))))
  .map((([e, t]) => {
    let x = t.quantity
    return e.includes("玻璃") && ("无" === 底玻 || "无" === 面玻) && !e.includes("单玻") && (x = Math.round(t.quantity / 2), …),
      t.materialName + ":" + t.result + "*" + x * 数量
  }))
```

解码（`legacy/decode-stringmap.mjs`）：`_0x11f592(995)` = **上亮横**、`_0x11f592(1080)` = **上亮窗玻璃**。
⇒ 关键词数组与我们一致 ✅，但**匹配对象是 KEY**，我们是 `materialName` ❌。

### 1.0 真机复现（2026-09-15，CDP 跑 /hui）

公式 80 `平开`，一行：平开门 / 2000×900×100 / 白玻+单玻 / **亮窗总高 2500**（> 门洞高，走到「有上亮」分支）。
生产单预览单元格实测：

```
门扇      : 光企高:2000*2  上下方:900*2  玻璃高:2000*1  上亮玻璃高:500*1  玻璃宽:900*1  上亮玻璃宽:900*1
外框      : 门框高:2000*4  门框宽:900*2
亮窗/扣板 : 扣板高:2000*2  扣板宽:900*1  扣板厚:100*1        ← 少了「上亮玻璃高 / 上亮玻璃宽」
```

**亮窗/扣板列丢了两个件**：KEY = `上亮窗玻璃高` / `上亮窗玻璃宽` 命中关键词 `上亮窗玻璃` ✅，
但它们的 materialName 是 `上亮玻璃高` / `上亮玻璃宽`，**不含 `上亮窗玻璃`** ❌ → 被我们过滤掉。
（旧版按 KEY 匹配 → 会输出 `上亮玻璃高` / `上亮玻璃宽` 两行。）

### 1.1 为什么这会出错

`formulas.parts` 的 KEY 带前缀/限定词，`materialName` 是裸名。库里实测：

| 公式 | key ≠ materialName 的部件数 |
|---|---|
| 80 `平开` | 2 / 11 |
| 81 `ZZ推拉测试` | **24 / 31** |

差异形态（公式 80/81 实库导出）：

| KEY | materialName |
|---|---|
| `上亮窗玻璃高` / `上亮窗玻璃宽` | `上亮玻璃高` / `上亮玻璃宽` |
| `无亮窗边封` | `边封` |
| `2轨上滑` / `2轨下滑` | `上滑` / `下滑` |
| `2轨4扇收口` | `收口` |
| `无亮窗单包宽` / `无亮窗双包宽` | `套线宽` |
| `2轨2扇上下方` / `2轨4扇玻璃宽` … | `上下方` / `玻璃宽` … |

**漏件**发生在「关键词命中 KEY、命中不了 materialName」时，例如：
- 关键词 `上亮窗玻璃`：KEY `上亮窗玻璃高` 命中 ✅ / materialName `上亮玻璃高` 不命中 ❌ → **该件被我们丢掉**
- 关键词 `亮窗`：KEY `无亮窗边封` 命中 / materialName `边封` 不命中

**错件/选错件**发生在「按名精确取件」处（`parts.find(p => p.materialName === k)`）：
旧版若用 `hasOwnProperty(KEY)` 取件，我们按 materialName 取就会**取到另一个件**或取不到。

### 1.2 已经做对的地方（对照）

同一文件里「吊趟 · 外框 · 套线组」我们**已经**按 KEY 匹配（理由与之一致，见 `Hui.vue:4126-4130` 注释），
说明这个坑此前已被局部发现，只是没有推广到其它列。

## 4.2 `底玻`/`面玻` 空串 —— 已查明根因并修复（2026-09-15）

两条独立审计（门扇、亮窗）都点到「旧版严格判 `"无" === 底玻`，我们把空串也当无」。追下去发现
**根因不是判断写宽了，而是我们的默认值本身就不对** —— 原版根本不会产生空底玻：

```js
// @36957 平开表
F  = Vue.ref(localStorage.getItem("BottomGlass")    ?? (X("磨砂"), "磨砂"))   // 默认底玻 = 磨砂
ee = Vue.ref(localStorage.getItem("GlassThickness") ?? (Z(4), 4))            // 默认玻璃厚 = 4
// @147180 移门表（键名与平开相同，回落值不同）
O  = Vue.ref(… ?? (k("白玻"), "白玻"))                                       // 默认底玻 = 白玻
L  = Vue.ref(… ?? (D("左前"), "左前"))                                       // 默认开向 = 左前
// 新建行工厂 @39301 / @149781
{ "底玻": F.value, "面玻": "白玻", "玻璃厚": ce(), "开向": L.value }
```

即：**新建行就是双玻（磨砂/白玻 + 白玻），不折半**。我们原先 `LS.get('BottomGlass') || ''`
且**从不写这个键**，于是每一行都是空底玻 → 被当成单玻 → 折半。

**并且旧版有「改值即设为默认」**（仅平开表；`le`/`ne`/`te` 定义 @36957，调用 @75380 / @75890 / @77100 / @93688）：

| 改什么 | 写哪个键 | 提示 |

| 玻璃厚 | `GlassThickness` | `已将"Xmm"设为默认玻璃厚度` |

### 4.2.2 ⚠️ 方向修正：**旧版底玻/面玻是必填，空串根本不存在**

用户指出「旧版底玻必填，没有空串一说」，查证属实 —— 而且说明 §4.2.1 那轮**把重点搞反了**：

**证据一：两格都没有 `clearable`**
- 底玻格：`@75060`（平开）/ `@185271`（吊趟）—— props 只有 `modelValue / onUpdate / class / fetch-suggestions / onInput / onSelect / onFocus / onBlur`
- 面玻格：`@73314`（平开）/ `@183565`（吊趟）—— 同样无 `clearable`
- 对照：**玻璃厚**格 @77100 是**有** `clearable` 的

**证据二：必填清单里含底玻/面玻**
```js
// @349085 平开
const x = ["型材","数量","颜色","底玻","面玻", 玻璃厚, "开向", 计价方式]
// @353602 吊趟
const x = ["型材","颜色","底玻","面玻", 玻璃厚, "开向","扇数", 轨道种类,"扇数"]
for (const e of x) {
  ;( (e === 玻璃厚 ? (行[e] === undefined || 行[e] === null) : !行[e])
     || ("门洞高"===e && 行[e] <= 0)
     || ("门洞宽"===e && 行[e] <= 0)
  ) ? (行.errorFields[e] = true) : (行.errorFields[e] = false)
}
```
两格的 `class` 也确实挂了 `{"error-cell": 校验结果["底玻"]}`。

**证据三：新建行默认值非空**（磨砂·白玻 / 白玻·白玻，见 §4.2）

⇒ 三条合起来：**旧版从任何入口都产生不出空底玻**。所以 §4.2.1 的 15 处严格比较
在旧版模型下是**不可观测**的 —— 它们是「照原文对齐」（正确且与原版逐字一致），
但**不是**真问题；真问题在我们这边：

| 我们 | 旧版 |
|---|---|
| `missingFieldsOf` **没有**底玻/面玻 | 两格都是必填 |
| 玻璃下拉**加了** `clearable` | 两格都没有 `clearable` |
| 于是空串可达 → 才需要 `\|\| '无'` 去兜 | 空串不可达 |

**已修**：`missingFieldsOf` 补 底玻/面玻；`cellError` 补 底玻/面玻 红框；
`glassSelectCell` 去掉 `clearable`。至此空串在我们的 UI 上也不再可达，
与旧版一致；那 15 处严格比较转为**纯防御性**（保持与原文一致，不改回）。

### 4.2.3 顺带发现（**未处理，待定**）：原版必填清单里没有 门洞高/门洞宽

@349085 / @353602 的校验循环里有 `"门洞高"===e && 行[e]<=0`、`"门洞宽"===e && 行[e]<=0`
两条，但 **`e` 只遍历清单 `x`**，而 `"门洞高"/"门洞宽"` **不在 `x` 里** ⇒ 这两条**永不命中，是死代码**
（看形态像当初漏加了清单项）。

我们目前**保留了**「门洞宽/门洞高 > 0」为必填（比原版**更严**）——
删掉会放开「尺寸为 0 也能保存」，属另一个决定，故未擅自改。**待定**。
