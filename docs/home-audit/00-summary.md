#### ⛔ 第 7 条：刻意不做（回源码查证后）

旧版删除前的 `await y("删除")` **不是本地口令**，是**服务端校验**：

```js
if (!skipGate && !["恒泰智门33","恒祥门业","临泉县品匠移门"].includes(registrant)) return true
const r = await axios.get("https://www.samrtdoor.com.cn/1",   // ← 【旧版生产域名】
  { params: { param1:"login", param2:registrant, param3:pwd } })
```

⇒ ① 服务端校验；② **只对写死的 3 个租户生效**；③ 校验目标是**旧版生产服务器**。
**照抄 = 让新版去调旧版生产域名**（跨系统对外请求）⇒ 按本仓库既有口径不实现，
代码里留了三条候选路径供拍板。**不落「看起来在验、其实验不了」的假闸门。**

#### ❌ 第 11 条：审计描述不准

审计说两张子表「`v-show` 互斥切换」。实测旧版 `uo`（`Home.formatted.js:7653`）默认是
**`{ping:true, diao:true}`（两张都显示）** ⇒ **我们的默认行为本来就是对的**。
那个 `v-show` 是「默认都显示 + 子表组件内部可切」，切换在子表组件里
（带 `showPingkai` prop 的 Hui 组件，未移植）。**不是互斥。**

#### ⚠️ 另纠正一处审计误判

审计说旧版有「工具栏全选 checkbox」。回源码：**没有** —— `Oo`（`:7743-7759`）是
**el-table 表头全选格**的 `onSelectAll` 处理函数，不是工具栏控件。

#### ⚠️ 已更正：第 8 条是**误报**

审计说「新版不碰 `due_date`，改完日期后『临近截止』会算错」。**实测推翻**：

新版**根本不存这一列**，而是在 SQL 里推导
（`orders/service.rs` 的 `HEADER_COLUMNS`：`to_char(order_date + production_days + 1, 'YYYY-MM-DD') AS due_date`）。

实测（真实订单，改完已复原）：

```
order_date=2026-09-15  →  due_date=2026-09-16
order_date=2026-01-05  →  due_date=2026-01-06     ← 自动跟随
```

**数学上也等价**：SQL 的间隔是 `production_days + 1`，旧版的 `ceil((原截止日期 − 原日期)/天)` 同为 `production_days + 1`。
⇒ 旧版要**手动重算**（因为它存了那一列），新版用推导，**不变量反而更稳**。

教训：审计里这条是**只读了前端代码**、没看后端推导就下的判断。判定表里它本该标 `❓ 未确认`
（跨层行为要实测才算数），当时图快写成了 `❌ 未做`。

## E. 财务口径：删除订单红冲（2026-09-18 实测并修复）

二审时行操作那一路报过一句「实测留下孤儿 `finance_allocations`，客户未分配余额永久错」，
当时没查。这次查清了，是**两条独立缺陷叠加**，且**照抄旧版前端是错的**：

| 情形 | 删除前 未分配 | 删除后（旧） | 删除后（新） |
|---|---|---|---|
| 订单的钱来自**资金池分配** 300 | 700 | 400 | **1000** |
| 订单的钱来自**本单直接收款** 300 | 1000 | 700 | **1000** |

根因：旧版把整笔「已分配收款」写成**一条客户级负收款**（`order_id = NULL`）。
我们的 `未分配余额 = 实收金额 − 已分配总额`，而 `已分配总额` **只认带 `order_id` 的收款与
`finance_allocations`** ⇒ 负收款减了 `实收`、减不到 `已分配总额`，同一笔钱被减两次。

**端到端实测对照**（`finance-reversal-e2e.mjs`，走真 HTTP）：
客户往池子打 300 分给 A、另给 B 直接收 200，两张单删掉后 ——
旧写法 **未分配 −500 / 实收 0**（客户明明还有钱，账面倒欠）；
新写法 **未分配 300 / 实收 300 / 客户余额 −300**（自洽）。

修法（用户 2026-09-18 拍板「按来源拆」）：本单收款 → 带 `order_id` 的负收款；
池分配 → 负的分配行（新接口）。**这不是「偏离旧版」，是照抄旧版会错。**

## 四、这次审计本身的方法论

- **判定只有四个值**（已做/偏离/未做/未确认），没有中间态；**宁可标「未确认」也不猜**。
- **逐条给证据**：旧版字符偏移 + 新版 `文件:行`。没证据的不写。
- **既有文档只当起点、不当结论** —— 分析文档是分析阶段写的，实现变了它不会跟着变。
  这次就抓到 3 处文档与源码不符。
- **死代码 / 点了没反应的按钮单独记** —— 前几轮靠这条抓到「直接打印回执单其实是云打印」
  「导出PDF 在 ic=13/16 上必定报错」。
