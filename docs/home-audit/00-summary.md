## E. 财务口径：删除订单红冲（2026-09-18 实测并修复）

二审时行操作那一路报过一句「实测留下孤儿 `finance_allocations`，客户未分配余额永久错」，
当时没查。这次查清了，是**两条独立缺陷叠加**，且**照抄旧版前端是错的**：

| 情形 | 删除前 未分配 | 删除后（旧） | 删除后（新） |
|---|---|---|---|
| 订单的钱来自**资金池分配** 300 | 700 | 400 | **1000** |
| 订单的钱来自**本单直接收款** 300 | 1000 | 700 | **1000** |

根因：旧版把整笔「已分配收款」写成**一条客户级负收款**（`order_id = NULL`）。
我们的 `未分配余额 = 净收款 − 已分配总额`，而 `已分配总额` **只认带 `order_id` 的收款与
`finance_allocations`** ⇒ 负收款减了 `净收款`、减不到 `已分配总额`，同一笔钱被减两次。
（「净收款」= `Σ finance_payments` 含负数，是 `customer_balance` 内部那个 `paid`，
**不是**对外的 `实收金额` —— 后者是「累计充值」，分母不同。见 `docs/verification.md` 第 5 节。）

**端到端实测对照**（`finance-reversal-e2e.mjs`，走真 HTTP）：
客户往池子打 300 分给 A、另给 B 直接收 200，两张单删掉后 ——
旧写法 **未分配 −500 / 实收 0 / 客户余额 0**（客户明明还有钱，账面倒欠）；
新写法 **未分配 300 / 实收 0 / 客户余额 0**（自洽）。

⚠️ `实收 0` **两边都是 0，而且都对**：`实收金额` 是「累计充值」，只累加「收款里没分掉的那部分」，
本夹具两笔收款都没剩下。（2026-09-18 首次实测时这里记的是「旧 0 / 新 300」——
那个 300 是**我们的算法与旧版不同**造成的，2026-09-20 已对齐，别再把 300 当正确答案。）
区分两种写法的数是 **未分配余额**：−500 vs 300。

修法（用户 2026-09-18 拍板「按来源拆」）：本单收款 → 带 `order_id` 的负收款；
池分配 → 负的分配行（新接口）。**这不是「偏离旧版」，是照抄旧版会错。**
